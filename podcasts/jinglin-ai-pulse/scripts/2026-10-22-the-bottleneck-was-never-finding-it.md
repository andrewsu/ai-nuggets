# Ollie's AI Pulse — 2026-10-22

## Script

Here's what the AI world is talking about today. Yesterday the PHP project shipped an emergency patch for two critical vulnerabilities in its core engine, the NSA told organizations to take systems offline if they couldn't update immediately, and the disclosure site carried a headline you've probably seen by now: AI uncovers critical vulnerabilities in the backbone of the web. That framing is doing a lot of work, and the primary documents tell a more interesting story than the headline does. The models were fast. Everything that went wrong happened at human speed, in human institutions, for very human reasons. That's the thread running through today's episode.

Start with what actually shipped. Two vulnerability classes in core PHP, both rated nine-point-two, not a ten, despite what circulated early. One is memory corruption triggered when a request hits PHP's memory limit at exactly the wrong moment, leaving partially initialized data behind that PHP later treats as valid. The other is stale global state, where a fatal error leaves internal pointers aimed at memory from a previous request, so a later request on the same worker reuses freed memory. The researchers demonstrated pre-authentication remote code execution against WordPress, Drupal and Joomla using current container images, plus memory disclosure that leaks passwords, tokens and keys belonging to other requests. PHP runs something like seventy percent of websites. Both bugs sit in the parts of the engine every single request touches, which is exactly why they were so hard to fix without breaking compatibility or wrecking performance.

Now the part that reframes the whole thing. The PHP Foundation published its own account of how these were found, and the root cause was not discovered this year, and it was not discovered by a model. In 2024, PHP went through its first external security audit in years, run by Quarkslab, organized through OSTIF, funded by the German Sovereign Tech Agency. While fixing one of the issues that audit reported, a PHP core developer found the first signs of the memory problem. A potential exploit was theorized. No concrete attack vector was found. And then the fix stalled, for roughly two years.

The Foundation is unusually honest about why, and I want to quote them directly, because this is the most important sentence published in AI security this week. The security team developed several competing fixes, each with its own trade-offs — compatibility breaks, new denial-of-service potential, or changes to a large ecosystem of third-party extensions. The team, operating on consensus, struggled to choose between them and feared the repercussions of shipping the wrong choice. Their words: we won't pretend otherwise, the delay was a structural failure, caused by both the security team's decision process and its lack of resources.

So what did the AI contribute? Precision about timing matters here. A security firm called Calif began an audit of PHP under OpenAI's Patch the Planet program on July thirtieth. On August eleventh, a researcher there reported an unconditional remote code execution with the same root cause the project had found in 2024. OpenAI independently reported the same root cause the same day. Wiz followed two weeks later with further attack vectors. From August eleventh onward, fixing it became the top priority for everyone the Foundation funds.

That is the actual mechanism, and it's worth being precise about it. The models did not find an unknown bug. They converted a known theoretical concern into a demonstrated exploit. And the demonstration is what broke a two-year organizational deadlock. A consensus-driven team that couldn't choose between three unpleasant fixes suddenly could, because the cost of not choosing had become legible. If you want a one-line summary of what frontier models did for PHP security this year, it isn't "found a bug." It's "ended an argument."

The counterpoint went up on Hacker News last night and hit five hundred points fast. A developer writing as Elias Taylor published a post titled, bluntly, there isn't an easy exploit for this PHP vulnerability. His claim: there are literally thousands of proof-of-concept exploits on GitHub right now, and essentially none of them work against a vanilla PHP install. He ran them. Most lean on local file inclusion, meaning the exploit chain requires the target server to already have a severe vulnerability letting an attacker read arbitrary files. As he puts it, if you need that, this is not a severe bug.

But the interesting part of his argument isn't the skepticism. It's the explanation. He asks why so many people independently made the same bizarre error in judgment, and answers that they didn't make it independently. Their models made it for them. He calls these decision Schelling points — a method of solving a problem becomes wildly overrepresented because it's simply what the model does out of the box. You get a strange statistical signature where the errors are correlated rather than scattered, because they share an author. And in this case the shared error is almost funny: the model inserts a vulnerability into the test server in order to prove the server is vulnerable.

A commenter going by rf15 extended that into something genuinely new, and it's the sharpest idea I read all week. The standard objection to Taylor is that difficulty doesn't matter, because you only need expertise once and then everyone reuses the result. rf15's response: not if your model relies on existing code, and you collectively create a million repositories full of hallucinated broken implementations before a working public exploit exists, which later models then train on and retrieve from. The flood of confident garbage poisons the well for the next generation of attacker tooling. Accidental defense through data pollution. I don't know whether it holds up, but it's a real mechanism and I haven't seen it articulated before.

I should flag the pushback, because this is a live disagreement and not a settled one. Thomas Ptacek, who knows this domain about as well as anyone, declined to cosign Taylor's analysis, and his objection is clean: "I haven't seen a proof of concept I could get working" is not the evidence the author thinks it is. Server-side memory corruption is genuinely annoying to weaponize, and absence of a public exploit ten hours in tells you less than it feels like it does. Meanwhile the Foundation's own record says their team monitored the proofs of concept appearing after the leak and did not identify any functional exploit at the time of release — which supports Taylor on the facts while leaving Ptacek's point about inference entirely intact.

Then there's the coordination failure, which is where the humans really come off badly. The Foundation's timeline: on October twentieth, the two vulnerability identifiers began circulating with a wrong release time and a wrong severity score of ten-point-zero. No technical details leaked, but the project pulled its pre-announcement forward and moved the release up a full day. A Hacker News user named petecooper has since publicly taken responsibility for the original post, saying his contact told him there was no embargo and that this turned out to be a lie. Then Calif — one of the firms that reported the bugs — mistakenly published a marketing video demonstrating their proof of concept against live targets, complete with, I am not making this up, an anime girl. Copies circulated immediately. And then, more than six hours before the coordinated release, Chainguard unilaterally shipped patched images, letting anyone study the fix in binary form while everyone else waited.

The community split cleanly on that, and both halves have a point. One camp says Chainguard torched weeks of work by many parties. The other says embargoes make sense only while nobody is exploiting the bug, and once exploits circulate the responsible move is to ship. But the observation I keep coming back to is from a commenter called Tadpole9181: for a good twelve hours, nobody outside the embargo knew what was going on. There was a critical remote code execution affecting everyone, the people who knew were saying nothing except that your mitigations wouldn't work, and the Cloudflare CTO was posting about exploit traffic. The Dutch National Cyber Security Centre took itself offline. That wasn't a capability failure. That was an information failure.

Which brings me to the policy argument this kicked off, and it's the one I'd actually watch. A researcher posting as s1r1us listed a series of serious findings this year that he credits to OpenAI's Daybreak program giving vetted researchers model access — the PHP work, GitLab remote code executions, a full Chrome chain, a WordPress RCE. Then he argued OpenAI is making a mistake restricting access to its more capable models. His framing: there's a temporary capability gap defenders could exploit, and we shouldn't waste it. Put researchers through vetting, vet them as hard as you like, but drop the red team versus blue team distinction — give a thousand vetted researchers the best available models and monitor the hell out of their usage to detect abuse. Whatever you think of it, that's a concrete institutional proposal rather than a vibe, and OpenAI's own position partly concedes the premise. Their announcement says, in their words, that AI is accelerating vulnerability discovery, but discovery alone does not protect users, and that many maintainers are being asked to sort through more reports, more quickly, with the same limited time and resources.

The Foundation supplies the number that makes that concrete. Since the first of July, the PHP security team has published fifteen CVEs — and worked through more than a hundred reports that turned out to be invalid, duplicates, or not reproducible. Hold onto that ratio. It comes back.

One note on the emotional register, because the discourse split along a line that had nothing to do with PHP. Joshua Achiam at OpenAI posted that it feels like March first, 2020 for cyber, and speculated about internet lockdowns within months. Ethan Mollick read it as attack and defense accelerating at inhuman speeds against very human systems that have to react. And Kelsey Piper cut across both with one line: living in the shadow of annihilation is bad for people, even if they're right. I don't think she's rebutting the risk case. She's pointing at a cost the risk case doesn't price, and both things can be true.

To money, and the theme holds. Two announcements landed yesterday that are really the same announcement. Behnam Neyshabur's company Mirendil says its first pretrained base model was built by one researcher in three and a half months for less than ten million dollars in compute — and that figure covers the research and small-scale experiments, not just the final run. They put the base model in the one hundred billion to five hundred billion parameter range, with larger variants above that. Independent evaluations and API access are still to come, so treat this as an unvalidated claim about efficiency rather than a result. But Neyshabur's own framing is the line I'd keep: the bottleneck shifts from the size of a team to the ambition and judgment of the people directing them.

Same day, Richard Socher's Recursive released Flint, an Apache-licensed coding model — roughly forty billion total parameters with two and a half billion active, small enough to run in about twenty-four gigabytes locally at over a hundred and twenty-five tokens a second on a MacBook Pro. The benchmarks are self-reported and unreplicated. The part that matters is how it was built: Socher says their automated research system ran the full loop — ideation, implementation, validation, then deciding what to try next — and contributed the sparser model shape, the low-bit training that shrank the model by seventy-one percent with almost no quality loss, and custom kernels. From scratch in under four months, by a very small team.

So the capital story and the security story are converging on the same claim. Capability is getting cheap and abundant. Judgment is not. The scarce resource is a person who can decide which of a hundred findings deserves attention, and which of three bad fixes to ship.

Which is the perfect setup for today's deep cut, from a Latent Space essay published yesterday by Dan McAteer, called "Claude Mods: Flipping the Harness Inside Out." The argument chain is clean, so let me lay it out properly.

Premise one: as models absorb more and more of the agent harness into their own weights, the part of the harness that's left over is the part that faces the human. Premise two: that residual layer is therefore not a technical interface anymore, it's an attention interface — the layer that decides when the agent interrupts you, what it shows you, and which decisions it actually needs you to make. Premise three: historically the harness pointed from the agent toward the machine, letting the agent run commands and edit files. Mods reverse that direction, pointing it from the agent toward the human operator. The conclusion he's betting on: the harness becomes a platform that other companies build on, with models as the engine, the way the browser became a platform for web apps.

His example of why this matters is mundane in the best way. He asked Claude Code to simplify some UI text. The agent trimmed the copy, installed the build, took before-and-after screenshots. Everything looked finished. Then a built-in side agent called You Should Know — which watches the main agent and flags things buried in the trace — pointed out that the file being edited already had uncommitted work in it, and so did about forty-five other files. If he'd discarded the demo edits, he'd have thrown away that earlier unfinished work too. The agent did the task correctly. The interface caught what doing the task correctly would have destroyed.

And then McAteer does the thing that makes this worth your time: he reports his own failure, with a number. He built a supervisor mod that runs after any turn that edits a file, runs a command, or makes eight or more tool calls. In practice that's nearly every turn — ninety-nine of his hundred and eleven turns since he installed it a week ago. His conclusion: when a mod speaks up on almost every turn, I start skimming past it, which defeats the point of an attention interface. He also flags the costs, roughly five to six thousand extra input-equivalent tokens per check, and the trust problem — mods are not sandboxed, run with your permissions, see every prompt you send, and keep running even in safe mode.

Now put that next to the PHP number. The security team: fifteen real CVEs, over a hundred invalid or duplicate reports. McAteer: ninety-nine alerts across a hundred and eleven turns, and he starts skimming. That's the same failure, at wildly different scales, in completely unrelated institutions. Alert fatigue is the binding constraint on both — and in both cases the system generating the alerts is getting cheaper and faster while the system triaging them is not.

So here's the takeaway I'd hold onto. The story the headlines told yesterday was that AI found a catastrophic bug in the backbone of the web. The story the primary documents tell is that a human audit found the root cause two years ago, a human committee couldn't decide how to fix it, a model made the consequences undeniable, and then four separate human coordination failures in thirty-six hours — a leak, a marketing video, a broken embargo, and twelve hours of silence — did more to put sites at risk than the vulnerability demonstrably did. Finding things is solved. Deciding what to do about the things we find is not, and nothing shipped this week moves that.

One thing to watch tomorrow. Whether a working public exploit actually materializes. Taylor's argument and OpenAI's defender's window framing make opposite predictions, and the next few days adjudicate between them cleanly. If a reliable chain appears quickly, the skeptics were reading ten hours of silence as evidence of difficulty when it was evidence of nothing. If a week goes by and the only things on GitHub are still a million variations of the same broken local-file-inclusion trick, then rf15's self-defeating-models argument deserves a much more serious look than anyone has given it. Either way, we'll know soon, and the answer tells you something real about the gap between finding a bug and owning a server.

That's your pulse for today.
