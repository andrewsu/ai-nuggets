# IGVF Catalog — a three-billion-node variant-to-function knowledge graph with an MCP server for agents, where predicted coding-variant effects outnumber measured ones about five thousand to one

Paper link: https://www.biorxiv.org/content/10.64898/2026.11.20.768224v1

## Script

Most consortium data reaches the world as a portal full of files. You find the dataset, download it, work out its column names, and do the joining yourself. Today's preprint is the IGVF consortium's attempt to skip that step entirely, and it's the kind of resource that will quietly become the thing agents query when someone asks what a non-coding variant does. It comes from Ben Hitz's data coordination team at Stanford, the group that grew out of the ENCODE data center.

IGVF, the Impact of Genomic Variation on Function consortium, has over a hundred labs producing reporter assays, CRISPR screens, Perturb-seq, saturation genome editing and deep mutational scans, plus a set of groups building predictive models. The Catalog boils all of it down to one knowledge graph: roughly three billion nodes and eight point six billion edges across fourteen entity types. Variants, elements, genes, transcripts, proteins and pathways sit next to full ontology graphs for diseases, phenotypes, cell types and tissues. It all sits behind an eighty-six-endpoint API, Python and R clients, and an MCP server, so a coding agent can query it directly.

Two design choices are worth taking away. The first is how context is stored. An eQTL edge between a variant and a gene carries its p-value, effect size and source, plus a pointer to the ontology term for the tissue or cell type where it was observed. It's a hyperedge made from ordinary parts. If you followed last week's SPIDER episode, this is the same idea: a finding isn't a triple, it's a triple plus the conditions under which it held. Here, though, the conditions come from measurement metadata rather than being extracted from prose, so they can actually be trusted.

The second is the honest note about how agents should get in. The team built the obvious thing first, a retrieval-augmented setup where a language model reads the schema, writes a query in ArangoDB's query language, runs it, and summarizes the result. They say it was straightforward to build, and then they parked it as experimental, because token costs, load on the database and the sheer size of the returned results made it impractical. What worked better was handing Codex or Claude Code an MCP server. That server is a real product. Its six tools cover entity lookup with automatic type detection, genomic-region search, relationship discovery, translation between variant identifier formats, and source discovery. Its version number matches the Catalog release it targets. A contract test fails whenever the API drops or renames something the server depends on, and a new API endpoint fails the tests until someone decides whether to expose it. Anyone shipping a knowledge graph to agents should copy that: treat the agent interface as a versioned surface with tests, not as a thin wrapper you write once.

Now the part that changes how you should read the headline numbers. Of the eight point six billion edges, about five point nine billion are linkage-disequilibrium pairs from a public LD resource. Of the roughly one point six billion edges contributed by IGVF itself, about ninety-two percent are predictions, not measurements. Coding variants are the extreme case. The team enumerated every amino-acid change reachable by changing one codon, then loaded two whole-proteome predictors over them. That gives about one point one billion predicted coding-variant effect edges against about two hundred and ten thousand measured ones from VAMP-seq, saturation genome editing and similar assays. That's about five thousand predictions for every observation. There's a second asymmetry too: experimental results were loaded without filtering for significance, while predictions and public data were cut at dataset-specific thresholds.

None of that is a flaw. Predictions are exactly what you want for the variant nobody has assayed. But it means the most important property in the graph, for an agent, is the one that says whether an edge is observed data, a prediction, or a curated biological relationship. The API exposes that field and lets you filter on it. The MCP documentation talks about filtering by source and method; it doesn't present the observed-versus-predicted distinction as something the agent must report. An agent summarizing a variant as "the Catalog shows it disrupts binding" may be repeating a model output. The paper's own liver case study shows why it matters: for the GCKR missense variant, one predictor calls the impact modest while another scores it high, and only the base-editing screen settles that it acts through the protein.

That brings us to the main gap: nothing here evaluates the agent route. "Better success" with Codex and Claude Code is reported as experience, not measured. The three case studies, a FOXA1-dependent enhancer at a type 2 diabetes locus, the GCKR and HNF1A liver loci, and CDKN2A, CDKN2B and NOS3 in coronary artery disease, are explicitly described as reconfirming known biology. That's fine for a resource paper. The obvious next experiment is cheap, though. Give agents the MCP server and a set of loci with known mechanisms, then score whether they reach the answer, and whether they say which evidence was measured and which was predicted. That second score is the one that matters.

My take: this is what consortium data should look like when agents are the main readers. It's open, quarterly releases are built from infrastructure-as-code, every record is validated against a schema, and the agent interface comes with tests. Just remember that a graph this size is mostly LD and model output. The provenance class is the field that keeps an agent's summary honest, so ask your agent to report it every time.
