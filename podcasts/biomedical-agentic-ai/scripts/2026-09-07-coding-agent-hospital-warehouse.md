# Codex on a production Epic warehouse — the agent gets the right answer, just not the same one twice

## Script

Today's pick is a small, unusually well-designed study out of the clinical informatics division at Stanford Medicine Children's Health, posted to medRxiv over the weekend. The question in the title is the whole paper: can a general-purpose coding agent analyze a production hospital data warehouse? Not a purpose-built clinical tool, not a sandbox, not MIMIC. They took OpenAI's Codex agent, running G-P-T five point six, gave it read-only S-Q-L access to a full copy of their live Epic Caboodle warehouse through a dedicated service account with concealed credentials and no web access, and handed it ten analytic questions about pediatric ear infections — the kind of question their analysts field every week. Two S-Q-L analysts wrote the reference answers independently and blind to the agent, reconciled their disagreements, and had a pediatric infectious disease physician check the results for plausibility.

The surface result is the one you'd guess. Working autonomously, the agent never once wrote broken S-Q-L — all sixty baseline runs executed — and it never fabricated a value. At medium reasoning effort it landed within five percent of the analyst reference on twenty-seven of thirty runs. But it hit the exact number on only ten. Cranking reasoning effort to extra-high made it slightly worse, nine of thirty, for two point six times the tokens. That's a useful little data point on its own: whatever was going wrong here, more thinking was not the fix.

The finding I actually want to sit with is the one they lead their discussion with, and it's not about accuracy at all. Ask the agent the identical question three times and it returned the identical answer on only three of the ten questions. Forty-one of the sixty runs deviated from the reference somewhere. And when you chase down why, almost all of it collapses into a single decision. The base cohort of children with acute otitis media is either eleven thousand ninety-one patients or eleven thousand one hundred fourteen, depending on whether you count telehealth and video visits. The analysts excluded them. The warehouse, however, flags some of those virtual encounters as face-to-face — an institutional quirk that appears nowhere in the data dictionary the agent was reading. So on some runs the agent found it and on some runs it didn't, and because five of the ten questions are built on top of that cohort, that one twenty-three-patient wobble propagated into everything downstream.

Look at the error taxonomy and the shape of this gets very clear. Twenty instances of cohort-definition inconsistency. Eight cases of a valid query computing a subtly different quantity than intended. Six date-window errors. Six schema-linking errors. Zero syntax errors. Zero fabrications. Zero missing-data mishandling. The failures are all semantic. The agent is not bad at S-Q-L and it is not hallucinating — it is confidently answering a slightly different question each time, because the question as posed was underspecified and the warehouse won't tell it which reading is right.

And here's the detail that convinced me this is a real distinction and not a rhetorical one. On every task where the agent's count matched the reference, the authors went and checked whether it had found the same patients. It had — precision, recall and F-score all exactly one point zero, across six separate cohort tasks. This is not an agent producing approximately-right numbers by luck. Within a run it is rigorously self-consistent. It just draws the boundary somewhere else than you would.

Which means the fix is not a better model, it's writing the definition down. They tested that directly. Take the cohort definition an analyst corrected in one conversation, prepend it to the five dependent questions, re-run fifteen times: the denominator held at eleven thousand ninety-one on all fifteen runs, and thirteen of fifteen matched the reference exactly. Reproducibility restored, essentially for free. But the same experiment carries the warning label. One task — counting which children with recurrent infections got tympanostomy tubes — the agent got wrong by pulling from billing-charge records instead of the two procedure tables, reporting ninety-seven patients against a reference of fifty-five. It had all fifty-five, plus forty-two spurious ones. Five rounds of an analyst pointing at the problem in plain language did not dislodge it, and when they froze that definition and re-ran it five times, it returned the wrong answer five times out of five. The authors' line is better than anything I'd write: the agent reproduced a wrong definition as faithfully as a right one. Consistency is not correctness. It's just a precondition for noticing you're wrong.

One more thing, and it's the part I'd push back on the field with. In calibration, before the main study, they built the access layer the literature keeps recommending — a mediated Model Context Protocol server exposing a curated subset of tables. It was a disaster. Tables came one at a time, so the agent couldn't join across the ones most questions require; queries took ten to fifteen minutes and often didn't complete at all. They threw it out and gave the agent direct read-only S-Q-L over the entire warehouse plus its embedded data dictionary, and questions completed in one to two minutes. Their assessment is blunt: both designs had identical security controls, so the curated layer added the appearance of tighter security without any added protection, while starving the agent of the schema context it needed. Three days ago on this show we covered a Model Context Protocol server built on exactly the opposite intuition — narrow the surface, precompute nothing, let the model write native queries against curated endpoints. Both papers agree the retrieval layer should go. They disagree sharply about whether the curation layer should go with it, and this is the first study I've seen that actually measured the cost of it.

So the durable artifact here isn't the agent. It's the written-down definition — machine-readable, versioned, reusable across questions, the thing that turned an unreliable agent into a reproducible one in a single experiment. Every health system already has these definitions. They live in analysts' heads and in the S-Q-L files on their laptops. Getting them out of there and into a form an agent can consume is a data curation project, not an A-I project, and on this evidence it's the entire bottleneck.
