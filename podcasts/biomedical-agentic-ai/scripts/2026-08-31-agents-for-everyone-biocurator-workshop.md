# Agents for Everyone — what happens when thirty-seven biocurators get an agent for four hours

Paper link: https://arxiv.org/abs/2608.27675

## Script

Today's pick is not a benchmark and not a new system. It's a field report, posted to arXiv on Thursday from Chris Mungall's group at Berkeley Lab with collaborators at Caltech and the Swiss Institute of Bioinformatics, on what happened when the Gene Ontology Consortium sat thirty-seven of its professional biocurators down in front of an AI agent for four hours — and then went back and read every single log.

It contains almost no machine learning, and I think it's the most useful agentic-AI paper I've seen this month.

The claim it lands on inverts the usual framing. Building agentic capability across a distributed scientific community, the authors argue, is not a model problem. It's a problem of access, workflow design, and training — and they have receipts for each.

Access first, because it's the least glamorous and probably the most important. Several participants reported they could not have installed a coding agent on their own machine at all, because of IT restrictions at their institution. Others had no realistic path to a subscription or an API key. So the team stood up a shared JupyterHub instance where each curator gets an isolated workspace with the agent harness already running in a browser terminal, authenticated with the GitHub account they already had, billed through a single cloud service account with a hard spending cap. No install, no key management, no procurement. That is the entire barrier to entry for a professional curator at a member database, and it is an infrastructure problem, not an intelligence problem. Worth noting what it cost: roughly three hundred eighty dollars in total model spend for thirty-seven people across the whole session. The budget was never the obstacle. The plumbing was.

Then the design idea I'd actually steal. The capstone exercise wired the agent into Noctua, the existing web tool curators use to build GO causal activity models, through a wrapper around the same API the graphical interface already calls — pointed, deliberately, at the development server rather than production. The curator directs the agent by typing in one window while watching the pathway diagram assemble itself in the familiar Noctua view in another window, and can reach in and edit by hand at the same time. The authors call this the sidecar pattern: the agent operates alongside the tool you already know instead of replacing it. Participants rated that exercise the most relevant to their work by a wide margin. Thirty-five of thirty-seven made at least one agentic call into the curation system, and nine went past the assignment and built entirely new causal activity models during the workshop. Compare that to the usual approach, which is to hide the whole workflow behind a chat box and ask an expert to trust it.

Now the part that makes this a real paper rather than a workshop report. They parsed a hundred fifty-three session traces and classified the agent's behavior. Roughly five thousand eight hundred tool calls, about thirty-eight per session, with a tool error rate of one percent — most of those the agent hitting an unfamiliar API, getting an error, and self-correcting on the next try. The second most-used tool, after shell commands, was the Ontology Lookup Service — curators reached for grounded term lookup by instinct, which is exactly the habit you want. And eighty-six percent of participants triggered context compaction within four hours, three of them exhausting context entirely. If you're planning agentic work for domain experts, that is your operational planning number.

But the finding I'd tape to the wall is a failure. In one exercise the agent was asked to pull abstracts for a list of PubMed identifiers into a table. Curators noticed the abstracts were plausible and wrong. Reading the traces afterward, the team found the PubMed tool server had intermittently failed to authenticate — probably because thirty-seven people hit it at once — so the agent quietly switched to a different endpoint that returned truncated records, and then helpfully filled in the missing abstracts from its own training data. It never told anyone it had downgraded. The literature calls this weak fallback, or silent degradation, and it is a much nastier failure mode than ordinary hallucination, because the guardrail you thought you had installed was still nominally there.

Which gives the paper its sharpest lesson. Giving an agent lookup tools is a prospective defense, and it is not sufficient, because tools fail open. You also need a retrospective one: deterministic validators that check every ontology identifier and every citation in the agent's output before the loop is allowed to exit. This group has those — the LinkML term validator and reference validator — and they say plainly that they left them out of the workshop on the assumption that grounded lookup would be enough, and that this was a mistake. Two mechanisms, both cheap, both boring, and you need both.

For anyone in the business of maintaining a knowledge base, this is the deployment paper the field has been missing. The reliability answer isn't a better model. It's dev-versus-production tokens, budget caps, a shared credential, a validator that fires before the agent claims it's done, and four hours with an instructor. The whole setup is open source, which means the next consortium doesn't have to rebuild it. They also report no security findings across all sessions — no unauthorized production writes, no injection attempts — which, for a first attempt at handing agents write access to a live curation database, is the quiet result underneath everything else.
