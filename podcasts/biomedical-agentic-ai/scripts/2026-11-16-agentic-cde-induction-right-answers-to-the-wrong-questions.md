# Agentic CDE induction — an agent drafts a sarcoma data schema from 24,588 case reports, and the extraction is the easy part

Paper link: https://arxiv.org/abs/2611.18506

## Script

Usually, when we ask a language model to pull structured data out of the literature, we hand it the schema. Here are the fields, here are the allowed values, go fill them in. That part works well enough that it's close to routine. A new preprint from a Swiss group at Bern University of Applied Sciences and Inselspital asks the harder question: can an agent write the schema itself? Can it read a large corpus and decide what the common data elements should be, before anyone fills them in?

Common data elements are the NIH idea of a standardized question with a fixed answer format. Patient sex, as a value list. Maximum tumor dimension, as a number in centimeters. Normally a committee of experts sits down and writes them before looking at the data. That gives you control, but it's slow, and it misses whatever only shows up once you look at the whole corpus. Sarcoma is a good test case. It's rare and wildly heterogeneous, and much of what we know about unusual presentations lives in individual case reports written in free text.

So they pulled every sarcoma case report in PubMed, used a classifier to keep the single-patient reports, and ended up with 24,588 abstracts. Then the agent went to work, one abstract at a time, each in a fresh conversation with no memory of the others. For each abstract it proposed closed questions this report could answer, recording each one through a tool call. The runtime rejected anything that wasn't a proper question or had no value. That produced almost seventy-three thousand proposed data elements. Exact deduplication brought them down to about 7,800. Then came the interesting step. An agent took each element, pulled up to twenty near neighbors by embedding similarity, and decided which ones were really the same clinical variable, favoring precision over recall. After two passes of that, and a value-set cleanup, there were 1,570 master elements, each traceable back to every abstract that proposed it.

That number hides the first finding. Seventy percent of those 1,570 elements came from exactly one abstract. Only 53, about three percent, were proposed by at least fifty abstracts, and those 53 are what went forward. The threshold was chosen partly for cost. Extracting values means one model call per abstract per element, and the 53 already meant 1.3 million calls. So the schema that got used is the consensus core, and the long tail, which is exactly where rare-disease case reports earn their keep, was cut.

Extraction itself was done with plain, direct model calls, not an agent. They tried an agentic version first and dropped it because of the overhead. Every non-empty answer had to come with an evidence span that literally appears in the abstract, categorical answers had to match the value set, and failures got three retries. Everything ran on an open-weight model, gpt-oss-120b, on two Mac Studios, more than 1.4 billion tokens in total. That's a real point for anyone who can't send patient-adjacent text to a commercial API.

The extraction numbers look great. In a hundred sampled abstracts, the pipeline's answer exactly matched the expert reference in about ninety-five percent of the cases where either side had an answer. Sex, age at diagnosis, recurrence, surgery all landed in the mid-to-high nineties. The misses were in anatomy and time: primary lesion location was right only about seventy percent of the time, which makes sense, because a span can be real and still describe the metastasis instead of the primary, or count a duration from the wrong starting point. An evidence span shows the words were in the abstract. It doesn't show the model read them correctly.

But the schema review tells a different story, and it's the real result of the paper. Two clinicians rated each of the 53 elements for correctness, relevance and clarity. Only nineteen passed all three with both reviewers. Barely more than half were judged correct by both. The consolidation agent, despite two passes, left three separate age fields, several overlapping histology fields, and two fields asking for primary tumor location in different words. One tumor-size element offered specific measurements and the word "large" as answers in the same value list. So you get high agreement on the values and low approval of the questions, both at once, and the first number tells you nothing about the second. A pipeline can answer the wrong question very precisely.

One more detail deserves attention. The two clinical reviewers barely agreed with each other. Their kappa for correctness was 0.24, and for clarity it was slightly negative, which is worse than chance. So even the human gold standard for "is this a good data element" is soft. That's not a knock on the reviewers. Schema quality is a judgment about purpose, and nobody told them what the schema was for.

And that's my main criticism. The paper never compares its induced schema to the standards that already exist. NCI's own sarcoma case report forms carry CDE identifiers, oncology has mCODE, and the NIH CDE repository is right there. Mapping the 53 against those would tell you what the agent rediscovered, what it got wrong, and, most interesting of all, what the corpus says that the committees missed. That third category is the whole argument for inducing schemas from data, and it's unmeasured. The extraction evaluation also skipped empty answers, so recall is unknown, and it used the same corpus the schema was built from.

Still, I like this paper because it's honest about where the difficulty actually is. The authors' own conclusion is that the agent should draft the schema and humans should curate it before the big extraction run, with automated checks for duplicate questions and broken value sets in between. For anyone building knowledge graphs or ontologies from literature, the lesson carries over. Filling slots is now cheap and accurate, so it isn't the bottleneck anymore. Deciding what the slots should be is still the scientific work, and it needs grounding in an existing vocabulary and a reviewer who knows what the data is for.
