# KRAKEN — a biomedical knowledge graph built to be read by agents, not just people

Paper link: https://www.biorxiv.org/content/10.64898/2026.08.18.745544v1

## Script

Today's pick is a knowledge graph, which sounds like the least agentic thing I could bring you. That's exactly why it's interesting. It's called KRAKEN, out of the Institute for Systems Biology, built under the ARPA-H PATH program, and it went up on bioRxiv this week.

Start with the gap it fills. Almost every general-purpose biomedical knowledge graph you can name — Hetionet, PrimeKG, SPOKE, RTX-KG2, ROBOKOP — was built to answer one shape of question. Which gene is implicated in this disease, which compound might be repurposed against it, what mechanism connects the two. Good questions. They are also not the questions a deep phenotyping cohort generates. If you profile untargeted metabolomics, plasma proteomics, gut microbiome, clinical chemistries and polygenic risk on the same people over time — and crucially, on people who are not sick — what comes out is a mixed feature list. Metabolites named by the mass spec vendor. Proteins named by the affinity panel. Clinical chemistries named by whatever the local lab calls them. Polygenic scores, questionnaire instruments, derived measures like biological age and biological body mass index.

Most of those are not resolvable entities in any existing graph. Metabolites and lipids show up mostly through drug-target and disease-association edges, not the functional and structural classifications a metabolomics platform actually reports. Questionnaire instruments and polygenic scores usually are not entities at all. So you have a knowledge graph, and you have your data, and there is no way to put them in contact.

KRAKEN's answer is to take the Translator ecosystem graphs and add what they are missing: RefMet, the LIPID MAPS structure database, the NIH Common Data Elements repository, the Polygenic Score Catalog, derived wellness measures. Fifteen million nodes, a hundred and thirteen million edges, sixty-two Biolink entity types, still on the Biolink Model so it stays interoperable with everything else in the Translator orbit.

Now the part I actually want to talk about. The paper makes a claim I have not seen stated this cleanly: that readiness for agentic consumption is a design property a knowledge graph can have or fail to have, and that nobody has defined what it means. The Cypher and TRAPI endpoints we all query these graphs through were specified before agents were a consumer. So the authors wrote down what they think it takes.

It is less glamorous than you would hope, and that is the point. There is an MCP server alongside the web interface and the REST API — same tools, three doors. The MCP tools have three response modes: slim, full, and preview. Preview returns just the count, so an agent can size a query before committing its context window to the answer. Errors come back as structured responses with status codes rather than prose, so an agent can branch on a failure instead of hallucinating through it. And discovery tools let an agent enumerate the available ranking presets, constraint fields and operators at query time, rather than guessing at an API it was never trained on. None of that is research. All of it is the difference between an agent that can use your graph and one that burns eight thousand tokens finding out it cannot.

The second thing worth your attention is an editorial stance on integration that cuts against the grain. The usual move when you harmonize sources is to map each source's predicate onto the nearest term in your shared vocabulary. That is what makes graphs interoperable, and it silently discards the distinction the source was drawing. KRAKEN's position is: do not reconcile. Keep the original predicate and the source-specific properties on the edge. When one source says upregulates and another says affects with a direction and an aspect qualifier, keep both, unreconciled, side by side. Keep every merged identifier visible on the canonical node. Their argument is an asymmetry — a user who disagrees with a hidden reconciliation cannot undo it, whereas a preserved distinction can simply be ignored. I think that is right, and I think it is a harder discipline to hold than it sounds.

Provenance travels the same way. Every edge carries a knowledge level and an agent type, so you can see that roughly fifty-three million edges are computational predictions and about thirty-one million are manual curation, and you can weight or filter results by how much you trust each.

The engineering claim that made me sit up: the whole thing rebuilds, entity resolution included, in under three hours on a laptop, with peak memory under forty-eight gigabytes. A hundred-and-thirteen-million-edge graph. They get there partly by not recomputing what Translator already normalized. What that buys is real — schema changes become cheap to test, and the graph can be regenerated as its sources move.

They demonstrate it on five hundred and forty-three analytes associated with biological body mass index. Node search resolved four hundred and eighty-two with minimal hand curation, and the sixty-one failures were almost all unnamed spectral features that carry no chemical name to match. That is an honest failure mode rather than a hidden one.

Two caveats. The graph is served, not distributed — no bulk download, because the licenses of a hundred-plus ingested sources will not allow it. And KRAKEN validates none of its assertions; it inherits every error its sources make. On the first, the cheap rebuild is arguably the answer: the build code is public under an MIT license, so you can make your own copy in an afternoon. On the second, at least the provenance is there to catch it with.
