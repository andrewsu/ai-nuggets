# ddkg.skill — a knowledge graph's query know-how shipped as a versioned agent skill, and the cautions only worked once they became checks

Paper link: https://www.biorxiv.org/content/10.64898/2026.09.26.754400v1

## Script

Anyone who has tried to query a big integrated biomedical knowledge graph knows the dirty secret. The hard part is not the query language. It is knowing the graph. Which source abbreviation names a relationship and which one names an identifier namespace. Which direction an edge runs. Whether ClinVar was ingested whole or filtered. Whether one gene shows up as two rows because the graph stores a relationship and its inverse. Get any of that wrong and you do not get an error. You get a perfectly plausible table, or an empty one, and nothing tells you which.

Today's preprint, from Deanne Taylor's group at Children's Hospital of Philadelphia with Jonathan Silverstein at Pittsburgh, takes that problem seriously for one specific graph: the Data Distillery Knowledge Graph from the NIH Common Fund Data Ecosystem. It is built on the Unified Biomedical Knowledge Graph framework, on top of UMLS, and it pulls together more than a hundred and eighty ontologies with Common Fund datasets like GTEx, 4DN, LINCS, HuBMAP, Kids First and MoTrPAC, plus ClinVar, the Human Phenotype Ontology, Reactome, STRING and UniProt. A wonderful resource, and famously hard to query unless you helped build it.

Their answer is not a fine-tuned text-to-Cypher model. It is an Agent Skill, the open packaging format Anthropic introduced, which any compatible assistant can load. The interesting part is how they structured it. Instead of one big prompt, there is a small controller file, and a routing table that links topics to the pieces of reference material that bear on them, with relations like "must read with", "invalidated by" and "supersedes". A little script checks that those links still resolve. Behind that sit curated notes on traps found by actually running queries, plus machine-readable inventories of the release: two hundred eighty-nine source abbreviations, about twenty-one hundred relationship types, and roughly twenty-five thousand classified subject-predicate-object combinations. So a question about a dataset no worked example ever touched can still be composed from the inventory. The whole bundle is pinned to the December 2025 graph release and identified by checksum, so you can say exactly which build wrote your query.

Three design choices are worth stealing. First, the skill never touches the database. It writes Cypher, you run it on your own instance, and only the returned rows get interpreted. That sounds like a limitation until you remember how many institutional graph installs sit behind firewalls. Second, it is forbidden from predicting results. No guessed row counts, no anticipated gene lists. Each query instead ships with the check that would tell you it went wrong. And third, there is an explicit order of authority: what was validated by executing against this release outranks the release documentation, which outranks the framework documentation. They adopted that rule after edge names changed between releases, and queries written straight from the docs returned nothing at all, with no error.

Now, the evaluation, and I want to be straight about how thin it is. Nine test questions, run on an earlier build of the skill. Of the seven that touched data sources absent from the worked examples, five came back correct when executed. There is no comparison against the same assistant without the skill, and the authors say so. Published skills benchmarks disagree sharply on whether skills help at all, from no measurable gain on most software engineering skills to big gains in healthcare, so the headline number here can't settle anything.

But the failures are where the paper earns its place. They sorted every failure into four bins: the reference said something false; the right fact was there but never consulted; the fact was missing; or the answer was correct but unhelpful. The second bin dominated early testing, and that is why the routing table exists. Knowing where a topic is documented is not the same as knowing what else bears on it. The first bin was the dangerous one. False statements in the skill's own reference material produced silently empty results, and two of them survived several rounds of human review. Only executing a query and reading the output exposed them. The pancreas expression test only succeeded after execution caught two wrong assumptions in the skill itself.

Here is the finding I would put on a sticky note. Rules phrased as something you can check in the generated query were applied more consistently than cautions, the negative "be careful when" statements that depend on the agent recognizing mid-composition that the situation applies. Their example: an early warning about sorting by a column with only a few distinct values and then truncating, which silently slices through tied groups. As a caution, it was unreliable. So they rewrote it as a countable test. If the sort column has fewer distinct values than the row limit, inspect the query. And cautions that could not be reduced to a condition like that were moved into the checking script, where they run whether the agent remembers them or not.

That is the take. If you maintain a knowledge graph, the know-how that lives in your curators' heads is a versioned artifact that belongs next to the graph, and it should be released with the graph. But when you write it down for an agent, every "be careful" is a liability. Turn it into a test the output can fail, or into code that runs regardless, or assume it will be skipped.

And one small result shows why row semantics deserves its own rule. Their eQTL-meets-chromatin-loop query returned five thousand rows. Those were twenty-five hundred real eQTL-gene pairs, each counted twice, because the graph stores both "located in" and "location of". The skill now asks, before every query, what one row is supposed to represent. Most of us should be asking that too.
