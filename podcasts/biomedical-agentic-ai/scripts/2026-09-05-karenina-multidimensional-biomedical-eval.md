# Karenina — an evaluation framework built to catch a biomedical agent being right for the wrong reason

## Script

Today's pick went up on bioRxiv yesterday out of E-M-B-L-E-B-I and Open Targets, with Julio Saez-Rodriguez's group in Heidelberg — the same orbit that gave us BioCypher and BioChatter. The tool is called Karenina, it's open source, and its premise is a complaint about how we currently grade biomedical language models. Most benchmarks pull a snippet out of a long response, check it against a key, and throw the rest away. That score cannot tell you whether the answer was grounded in the evidence the model actually retrieved, what it cost to produce, or whether an agent failed because its biology was wrong or because its code crashed. Karenina's move is to take a domain expert's plain-language description of what a good answer looks like and compile that into runnable evaluation specifications — answer templates, rubrics, multi-turn scenarios — then score against the full response, the tool trace, the saved workspace, and the run metadata.

The first case study is the one that should interest anyone who has stood up a biomedical Model Context Protocol server. The Open Targets core team supplied a hundred and forty-four real drug-discovery questions across six areas — target, disease, drug, variant, evidence, study — with free-text reference answers. Karenina drafted a structured check from each one, a human reviewed it, and then seven models answered every question twice over: once from parametric memory alone, once with live M-C-P access to the Open Targets Platform. Three replicates, seven judges, forty-two thousand judgments.

The headline is the one you'd expect and the one I'd be tempted to stop at. Tool access raised average correctness from fifty-one percent to eighty-one percent. On genetically informed variant questions, where the no-tool baseline was worst, it went from twenty-four percent to ninety-two percent. Grounding your agent in your API works.

The other three findings are why the framework exists. First: among answers that were correct and had tool access, about eleven percent were not supported by anything the model actually retrieved. It queried the platform, it returned the right answer, and the evidence in its own trace does not entail that answer. It knew it already, or it guessed. If you are running a benchmark that only checks the final value, those look identical to real retrievals, and you will conclude your data source is doing work it isn't. Second, a citation audit found that giving models tools didn't fix hallucinated references so much as launder them — fabricated PubMed identifiers were largely replaced by real papers cited for claims those papers don't support, which raised that failure's share of serious citation errors by forty percentage points. That's a harder error to catch and a worse one to ship. Third, cost: tool use consumed between twenty-four and a hundred and twenty-one times more tokens per question. Completely invisible on a correctness leaderboard.

The second case study asks what happens across a conversation instead of a single turn, and this is the number I'd actually put in front of a lab. They took correct answers and pushed back on them with a confident, plausible false alternative — an incorrect value from the same corner of Open Targets, curated by hand so it was genuinely wrong but hard to reject. Models abandoned their own correct answer fifty-seven percent of the time. Claude Haiku four point five caved in sixty-eight percent of turns. Having tool access did not protect them: three quarters of the reversals accepted the false claim without going back to check the platform. And note what that means about the first case study — a system that scores eighty-one percent on single-turn questions has not been tested at all on the thing that actually happens when a scientist argues with it. The one hopeful result is that a separate model watching the exchange as a guardrail flagged ninety-seven percent of the reversals, which suggests this failure is at least cheap to monitor even if it's hard to train out.

The third case study takes BixBench, regroups it into fifty-three open-ended coding tasks, and scores the saved code and notes alongside the answers. Two things fall out. Grading numeric answers on a graded scale with an explicit tolerance instead of a hard pass-or-fail moved accuracy from forty-eight to sixty percent and recovered two hundred and sixty answers that were within a hair of correct — so a meaningful slice of what we've been calling agent failure is rounding and annotation drift. And reading the traces with a rubric separates scientific failure from computational failure: one task scored thirteen percent while its code ran essentially clean, another scored twenty-two percent after fighting its environment. Those two numbers look the same on a leaderboard and they tell you to do completely opposite things — buy a better model, or fix your sandbox. They also found that switching the agent harness moved one model fifteen points while leaving the others flat, which is a reminder that a benchmark score is a property of a model-harness pair, not a model.

What I like here is less any single result than the shape of the artifact. An evaluation in Karenina is a specification you can publish, rerun, and fork — the authors call it a living benchmark, and the natural home for it is exactly the kind of community that maintains an ontology or a knowledge base, where the domain experts and the evaluation criteria already live in the same place. The honest cost, which they state, is that multi-dimensional evaluation is expensive in compute and in expert attention. Forty-two thousand judgments for a hundred and forty-four questions is not something you run on every commit. But if you maintain a biomedical resource and you are about to put an M-C-P server in front of it, the grounding number from this paper is the one to carry around: an agent hitting your API and returning the right answer is not evidence that it read your data.
