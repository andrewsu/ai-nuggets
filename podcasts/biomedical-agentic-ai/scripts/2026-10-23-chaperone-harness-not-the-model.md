# Chaperone — a protein design harness, and the finding that extra reasoning gets spent on plumbing

Paper link: https://www.biorxiv.org/content/10.64898/2026.10.19.759896v1

## Script

Today's pick is a piece of infrastructure rather than a model, and that's exactly why it's worth your time. It comes from the Institute for Protein Design at the University of Washington — David Baker's group — the tool is called Chaperone, it's open source, and the claim underneath it is one you can argue with: what currently limits autonomous protein design is not how well the agent reasons about structure. It's how much of the agent's attention gets consumed wiring one program into another.

Start with the problem they're solving. A modern design campaign might generate backbones with RFdiffusion 3, thread sequences onto them with ProteinMPNN, predict structures with AlphaFold 3, and score the result with something physics-based — and every one of those tools has its own file formats, its own install story, its own idea of what an input looks like. So the work of running a campaign is mostly plumbing, and the plumbing gets rewritten every time the hypothesis changes.

Their abstraction is almost embarrassingly simple, which is usually a good sign. They observed that essentially every biomolecular design tool does one of two things: it generates new candidates from existing structures, or it annotates existing candidates with new numbers. Both of those fit the same shape — a table in, a table out. One row per design, carrying its own structural history and its own metrics. They call each operation a block, and a block is just a small Python class that takes the table and returns an extended table. The tool itself stays a black box; the block only translates in and translates out. Because every design keeps its lineage, the whole campaign has a single source of truth, and because the engine chunks the table across cluster jobs and checkpoints intermediate results, a crashed run resumes instead of restarting. More than fifty tools now sit behind that one interface.

That's a nice piece of software engineering. What makes it a paper is what happens when you hand it to an agent. The authors built a design evaluation suite — nine tasks, real targets, real shared cluster, twelve hours and a handful of GPUs per run, and at the end the agent has to submit ninety-six sequence-diverse candidates that get scored by held-out pipelines the agent never sees. They ran the same frontier model twice: once with Chaperone as its tool interface, once as a baseline agent with web access, free to go install whatever it thought it needed.

The harnessed agents used eighty-six percent fewer tokens and sixty-four percent fewer GPU-hours. And the mean design pass rate went up, not down — from six percent to twelve percent. Cheaper and better at the same time, which should make you suspicious that the baseline was spending its budget on something other than science.

Then comes the result I keep thinking about. They swept reasoning effort — low, medium, high — for both setups. The baseline agents consumed a median of twenty-five million additional tokens for each step up in reasoning effort. The harnessed agents used under ten million tokens total, even at the highest setting. Read that again: the extra thinking capacity you pay for in a bare environment largely goes into regenerating scaffolding, not into exploring more design hypotheses. If that generalizes, a lot of what we currently report as agent capability is really a measurement of the agent's environment, and the cheapest way to make your agent smarter may be to stop making it build its own tools every time it wakes up.

That should sound familiar, because this show made the same argument four days ago about Munin, the self-hosted literature agent out of Leipzig — their claim was also that the harness, not the model, was what made the system work. Two groups, two domains that share almost nothing, arriving at the same conclusion in the same week. When that happens it's usually worth taking the claim more seriously than either paper alone would justify.

The honest caveats are in the paper, and they matter. The harnessed agents had their internet disabled because their tools were already installed; the baseline had to find and install things itself. So this compares a curated environment against a bare one, and it does not separate orchestration skill from structural reasoning. It's one model family, which the authors flag as a limitation. And twelve percent is still twelve percent — the absolute pass rates are low.

Where it gets concrete is the wet lab. They ran a two-week cortisol binder campaign, with a researcher steering and the agent executing: a sweep of twenty center-of-mass placements across four binder lengths, then sequence design with six different composition biases, then prediction and refinement cycles — a hundred and four small-scale runs before anything was scaled up. Twenty-seven candidates went to fluorescence polarization. The best one bound at one point three two nanomolar, with no affinity maturation at all. For comparison, the previous published effort on cortisol landed at sixty-eight nanomolar after computational design plus experimental maturation. They also built a twelve-subunit self-assembling nanoparticle, one of fifteen tested assembled correctly, and a rigid linker for crystal design that produced visible crystals.

Note what that cortisol story actually is, because it's the most useful framing in the paper. This was not an autonomous agent doing design. It was a scientist exploring a hundred-plus hypotheses in two weeks because the cost of trying one dropped to a few dozen lines of code. The agent was the lab-mate running the jobs, not the designer.

And the transferable lesson here isn't about proteins at all. It's that a single canonical schema — one table, one row per entity, lineage and metrics attached — is what made fifty heterogeneous tools legible to a language model. That's a data integration result wearing a protein design costume. If you want agents working across your tools, the leverage is in the interface contract, not the prompt.
