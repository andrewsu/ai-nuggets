# MErlin — a multi-omics toolkit shipped as an agent skill, where the skill's whole job is to say no

Paper link: https://www.biorxiv.org/content/10.64898/2026.09.02.748773v1

## Script

Today's pick is a bioRxiv preprint from the University of Florence, with collaborators at INRAE, and on the surface it is a bacterial epigenomics toolkit. That is not why it matters. It matters because it treats an agent skill as a scientific artifact worth publishing in its own right, and it arrives at a conclusion that runs directly against where most of this field is heading.

Start with the problem, because it is a data integration problem before it is anything else. A bacterial methylome means nothing on its own — it is a list of coordinates. It acquires meaning only against the annotation, the motif inventory, the methyltransferase complement, the transcriptome, position along the replication axis, and increasingly chromosome conformation. Six or seven layers, in incompatible formats, produced by different people sometimes years apart, using different identifier namespaces. And here is the part that should make anyone who has ever joined two genomics files wince. Every one of those integrations reduces to a join on a sequence identifier or a gene identifier, and both fail silently. If the FASTA carries a version suffix on the contig name and the annotation file does not, the inner join returns zero rows. No exception, no warning from pandas, from bedtools, from any obvious way you would write it by hand. The output is a table of zeros — which is precisely, and indistinguishably, what a genome with no methylation would produce. No stack trace, apparently valid output, and therefore it acquires a biological interpretation.

Now the inversion. Almost all of the agentic bioinformatics literature asks the assistant to write the analysis — generate a script, run it, debug it, iterate. These authors argue that for a mature, well-specified method this is the wrong division of labor, and their sentence on it is the best line in the paper: code generated on the fly is not reviewed, not versioned, not tested, and not the same twice, and its statistical choices are whatever the model happened to sample. So keep the implementation fixed and audited, and let the model supply what it is actually good at — parsing an unstructured request, inspecting messy inputs, asking the clarifying question, choosing among a bounded set of validated operations, and explaining the result.

MErlin therefore ships as two artifacts. The package is a seventeen-module command line toolkit that works fine from a terminal. The skill is a directory of instructions and reference documents, and it contains no analysis logic whatsoever. It is procedural knowledge about the package: a decision procedure mapping available inputs to eligible modules, mandatory pre-run checks, a list of questions a human must answer before anything executes, a mapping from experimental design to licensed claim, and an interpretation guide whose main function — their words — is to prohibit sentences. That guide exists chiefly to enforce the difference between "methylation co-varies with expression", which the tool can support, and "methylation regulates expression", which it cannot, at any p-value.

The reframing is worth stealing outright. The unit of scientific software distribution should extend from the program to the program together with the knowledge of how to use it. A package is a set of capabilities. A skill is capabilities plus the judgment about when to invoke them, what to check first, and what the answer is allowed to mean — the tacit knowledge that normally lives in the head of the group's bioinformatician and leaves when they do. Writing that down, they argue, has some of the same value as publishing a protocol.

What makes this more than a nice framing is that the constraint is architectural rather than conversational. Because the assistant selects among audited modules instead of writing code, it cannot quietly reach for a more permissive test. And because the statistical caveat is printed by the tool itself — a one-sample-per-condition design is stamped as such in the output table and in the provenance record, not asserted by the model — the constraint survives an enthusiastic user who wants a stronger story than the design supports. The failure mode becomes under-claiming rather than over-claiming. There is even a documented smoke test: if the assistant offers to write you a pandas script, the skill did not load.

The real-data illustration is a methylome and transcriptome comparison in an Antarctic marine bacterium across two growth media, specified entirely in natural language with no command typed, and the answer is a negative — no differential methylation accompanying a real transcriptional response. What sells it is that the tool volunteered three reasons to distrust itself: the one-sample-per-condition design means the false discovery rates screen candidates rather than establish differences; the sequencing platform's sparse modification encoding meant the coverage column was counting methylated reads rather than depth, so the differential test had to run on calls instead of fractions; and GC skew was too flat for reliable origin inference, so every spatial statistic was flagged unreliable rather than reported.

On reproducibility they take the honest position: a conversation is the interface, not the record. What is reproducible is what executed, captured in provenance sidecars with command lines, dependency versions and input checksums, plus a configuration file exportable straight to Nextflow or Snakemake. A session that produced a figure reduces to a config anyone can re-run deterministically with no assistant involved.

Be clear-eyed about the evidence, though. The claim that the skill changes what a non-expert obtains rests on exactly one worked example, and the authors say so. They then lay out the three-arm evaluation they have not run — assistant alone, assistant with the package but no skill, assistant with both — and correctly identify the middle arm as the informative one, because without it you cannot separate the contribution of the software from the contribution of the procedural knowledge. And then the sentence I would put on a poster: current benchmarks measure task completion, and they argue appropriate refusal deserves equal weight — that a benchmark whose top score requires declining several of the tasks would be a better instrument. Their design principle follows from it. A useful scientific skill should constrain the assistant's action and inference space at least as much as it expands access to the software. A skill that makes an assistant more capable of arbitrary analysis is a liability. A skill that makes it reliably refuse to run before checking a join is an asset.
