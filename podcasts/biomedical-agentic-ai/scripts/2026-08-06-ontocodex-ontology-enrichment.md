# OntoCodex — a five-agent pipeline that enriches biomedical ontologies and writes the OWL code to do it

Paper link: https://www.nature.com/articles/s44401-026-00117-9

## Script

Ontology enrichment is one of those tasks that everyone in biomedical data integration knows is a bottleneck and nobody enjoys. You have a formal ontology — classes, properties, a hierarchy, all encoded in the Web Ontology Language — and you need to keep growing it as new concepts appear: new lab tests, new drugs, new procedures for a disease. Traditionally that's a domain expert reading literature, deciding what belongs, figuring out where it slots into the hierarchy, mapping it to standard codes, and then hand-editing the ontology file. It's careful, slow, top-down work, and it doesn't scale.

A new paper in npj Health Systems, out of Cui Tao's group at Mayo Clinic, proposes OntoCodex, a multi-agent framework that tries to turn that manual loop into a semi-automated one. And what I like about it is the shape of the system, which is more mature than most "point an LLM at it" attempts.

There are five agents. A decision agent acts as the orchestrator — it reads the enrichment request, makes a plan, and hands out tasks. An ontology reading agent parses the existing ontology so everything downstream is grounded in the actual schema: the real classes, the real hierarchy, the real constraints. A knowledge base agent ingests the source corpus and pulls out candidate concepts. A terminology agent normalizes those concepts and maps them to standard vocabularies — SNOMED, RxNorm, LOINC, and the rest — by loading in the full OMOP standardized vocabulary set. And a script generation agent turns the validated results into executable Python that actually writes the new OWL file: creating classes, asserting subclass relationships, attaching annotations and codes.

That last agent is the real contribution. Most LLM-and-ontology work stops at extraction — it hands you a list of concepts and leaves the formal integration to you. OntoCodex closes the loop: concept discovery is coupled directly to ontology construction, with a human-in-the-loop checkpoint before anything gets written, and you can open the result in Protégé and inspect it. Crucially, the code generation is template-based and deterministic — the language model is used only to normalize messy inputs and map to the schema, not to freely write code. That's the right instinct. You don't want a stochastic model improvising OWL axioms.

They test it by enriching a common data ontology for multiple chronic conditions — built on OWL and aligned to the OMOP common data model — across five diseases: stroke, COPD, atrial fibrillation, osteoporosis, and Parkinson's. And here's where I want to be honest with you about what the evaluation does and doesn't show. Against baseline GPT-4o, OntoCodex generally extracted concepts more reliably and, importantly, was more conservative — it withheld predictions when the source had no answer instead of hallucinating spurious lab tests. On mapping specific medications to RxNorm codes it hit 100 percent correct versus about a third for the baseline. Those are real, sensible wins.

But look closely and the study is a feasibility demo, not a benchmark. The source corpus was MedlinePlus — patient-education material — chosen so two people could hand-check everything. The evaluation sets are tiny, so the confidence intervals are enormous, some spanning from thirty percent to nearly perfect. And the single biggest performance jump didn't come from agentic reasoning at all — it came from prompt engineering: when they changed the prompt from "list medications for this disease" to "use only this specific page and return exactly what's listed," precision went from about 0.53 to perfect. That's not intelligence; that's constraining the model to copy from a fixed source. Mapping was genuinely uneven too — strong for specific drugs, weak for lab tests and drug classes, because a patient-education page says "blood test" where LOINC wants a specific assay.

So don't read this as "LLMs now do ontology curation accurately." Read it as a well-engineered template for how the pipeline should be built. And that template is the valuable part for anyone doing knowledge engineering: ground every step in the parsed schema, normalize to OMOP so the output is interoperable with real-world data out of the box, keep code generation deterministic and reviewable, and put the human at the ambiguous decisions rather than in every loop. They also gesture at something I think is exactly right for the future — expressing enrichment as standardized change operations, using the Knowledge Graph Change Language, so ontology evolution becomes auditable and version-controlled instead of a series of opaque edits.

The bottom line: the accuracy numbers here are anecdotal and the corpus was deliberately easy. But the architecture — a schema-aware, OMOP-grounded, human-in-the-loop agent pipeline that ends in reproducible OWL artifacts — is a credible blueprint for making ontology maintenance a scalable, auditable loop instead of a manual craft. For the biomedical knowledge graph world, that blueprint is worth more than the benchmark.
